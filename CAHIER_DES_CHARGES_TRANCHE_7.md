CAHIER DES CHARGES

TRANCHE 7/8 — UX/UI, DESIGN SYSTEM ET EXPÉRIENCE UTILISATEUR

Version consolidée : 1.6


---

303. OBJET DE LA TRANCHE

Cette tranche définit l'apparence et l'expérience d'utilisation du centre.

L'interface devra être inspirée de l'esprit des plateformes universitaires modernes, notamment TELUQ, sans chercher à la copier.

L'objectif est de créer une plateforme :

sérieuse ;

académique ;

moderne ;

claire ;

sobre ;

professionnelle ;

mobile-first ;

facile à comprendre ;

peu distrayante.


Le design devra donner l'impression d'utiliser un véritable établissement de formation, et non une simple application de quiz.


---

304. PRINCIPLE DIRECTEUR DU DESIGN

L'interface devra respecter la règle :

> L'apprenant doit toujours savoir où il est, ce qu'il fait, pourquoi il le fait et ce qu'il lui reste à accomplir.



À aucun moment l'utilisateur ne devra être obligé de deviner :

quelle leçon il suit ;

quel niveau il suit ;

pourquoi une activité est verrouillée ;

pourquoi il doit réviser ;

pourquoi il a échoué ;

comment progresser.



---

305. IDENTITÉ VISUELLE

Le centre devra disposer d'une identité visuelle propre.

Elle comprendra :

nom du centre ;

logo ;

symbole graphique éventuel ;

palette ;

typographie ;

style des icônes ;

règles d'utilisation.


L'identité devra être suffisamment neutre pour convenir ultérieurement à plusieurs apprenants et éventuellement plusieurs formations.


---

306. INSPIRATION TELUQ

L'inspiration recherchée concerne principalement :

sérieux institutionnel ;

hiérarchie claire ;

espaces blancs ;

navigation structurée ;

lisibilité ;

présentation académique ;

information organisée.


Il ne faudra pas reproduire :

logo ;

éléments graphiques propriétaires ;

identité exacte ;

textes ;

interface à l'identique.


Le résultat doit être inspiré par le niveau de sobriété, pas une copie.


---

307. MOBILE-FIRST

Le téléphone sera considéré comme un appareil de première importance.

Chaque fonctionnalité devra être pensée d'abord pour un écran mobile.

Puis adaptée aux :

tablettes ;

ordinateurs portables ;

grands écrans.



---

Sur mobile :

↓

Navigation secondaire ou menu

Cette organisation permettra de conserver une navigation rapide.


---

309. HEADER

Le header devra afficher notamment :

logo ;

nom court du centre ;

niveau actuel éventuellement ;

accès profil ;

menu mobile.


Il ne devra pas être surchargé.


---

Dashboard

311. NAVIGATION MOBILE

Sur mobile, la sidebar deviendra un menu accessible.

Les éléments essentiels devront rester rapidement accessibles.

Une navigation inférieure pourra éventuellement être utilisée pour quelques fonctions majeures :

Home ;

Learn ;

Practice ;

Progress ;

Profile.



---

312. BREADCRUMBS

Sur les écrans suffisamment profonds, le système pourra afficher :

Course / Level 4 / Module 2 / Lesson 3

Cela permet à l'apprenant de savoir exactement où il se trouve.

Cette carte devra être particulièrement visible.

Elle indiquera :

activité ;

bouton Continue.

315. CARTE DE PROGRESSION

68 %

---

322. RÈGLE DE LISIBILITÉ

Une leçon ne devra pas être présentée comme un énorme bloc de texte.

Elle devra utiliser :

titres ;

sous-titres ;

paragraphes courts ;

listes ;

exemples ;

encadrés ;

exercices ;

espaces.



---

323. EXEMPLES LINGUISTIQUES

Les exemples devront être visuellement distingués du texte explicatif.

Exemple :

> I need to check the server.



Puis :

Meaning

Je dois vérifier le serveur.

Puis :

IT context

The technician needs to check the server before restarting it.


---

324. VOCABULAIRE

Les mots importants pourront être présentés sous forme de cartes.

Exemple :

DEPLOY

Verb

Deploy an application.

Meaning

Mettre une application en production/déployer.

IT

Deploy the new version to the server.


---

325. PHRASES MODÈLES

Les structures importantes devront avoir un traitement visuel particulier.

Exemple :

> I'm trying to + VERB



Puis plusieurs exemples.

L'objectif est que l'apprenant puisse remplacer progressivement le dernier élément et produire ses propres phrases.


---

326. EXERCICE

L'exercice devra apparaître dans un espace visuellement distinct.

Exemple :

Choose the correct answer

> I ___ to check the server.



A. need
B. needs
C. needing

Puis :

Check answer


---

327. FEEDBACK POSITIF

Lorsqu'une réponse est correcte :

> Correct!



Puis éventuellement une explication courte.

Le feedback devra rester sobre.

Pas d'animations excessives.


---

328. FEEDBACK EN CAS D'ERREUR

Lorsqu'une réponse est incorrecte :

> Not quite.



Puis :

Correct answer

et :

Why?

L'objectif est d'enseigner, pas seulement de signaler l'échec.


---

329. PROGRESSION PENDANT UNE ÉVALUATION

L'écran devra afficher :

Question 14 / 40

et une barre :

███████░░░░░ 35 %

L'utilisateur doit savoir combien de questions restent.


---

330. EXAMEN

Pendant un examen important, l'interface devra être plus dépouillée.

Elle devra éviter les distractions.

Éléments principaux :

question ;

réponses ;

progression ;

navigation ;

éventuellement temps restant si un temps limite existe.



---

---

333. CARTE DE RÉVISION

Exemple :

Irregular verbs

---

334. PAGE PROGRESS

Elle devra donner une vision plus complète que le dashboard.

Sections :

Overall

By level

By domain

By skill

Historical progress


---

335. GRAPHIQUES

Les graphiques devront rester simples.

Exemples :

progression dans le temps ;

score par niveau ;

maîtrise par domaine.


Le système ne devra pas transformer la formation en tableau de statistiques incompréhensible.


---

336. PAGE RESULTS

Elle devra conserver l'historique des évaluations.

Exemple :

Level 1 Assessment — 84 % — Passed

Module 3 — 79 % — Passed

Cumulative Review — 72 %

Level 4 Assessment — 88 % — Passed


---

337. PROFIL

La page profil devra rester simple :

identité ;

date de début ;

progression ;

niveau ;

résultats ;

paramètres ;

déconnexion.



---

338. ACCESSIBILITÉ

Le système devra viser une bonne accessibilité.

Principes :

contraste suffisant ;

textes lisibles ;

boutons suffisamment grands ;

navigation clavier ;

labels explicites ;

structure sémantique ;

messages compréhensibles.



---

339. NE PAS DÉPENDRE DE LA COULEUR

Une information importante ne devra jamais être communiquée uniquement par la couleur.

Exemple :

Mauvais :

🔴 = échec

Meilleur :

NOT PASSED

avec un indicateur visuel complémentaire.


---

340. TYPOGRAPHIE

La typographie devra privilégier :

lisibilité ;

distinction claire entre titres et texte ;

taille confortable sur mobile ;

espaces suffisants.


Le nombre de polices devra être limité.


---

341. BOUTONS

Les actions principales devront être immédiatement identifiables.

Exemples :

Continue

Start

Practice

Review

Check answer

Submit

Next

Les boutons devront utiliser des libellés explicites plutôt que des icônes ambiguës.


---

342. ÉTATS DES BOUTONS

Chaque bouton important devra prévoir :

normal ;

hover ;

focus ;

pressed ;

disabled ;

loading.



---

343. ÉTATS DE CHARGEMENT

Lorsqu'une opération prend du temps :

Loading...

ou un indicateur approprié.

L'utilisateur ne doit pas croire que l'application est bloquée.


---

344. ÉTATS VIDES

Lorsqu'il n'y a aucune donnée :

Exemple :

> No reviews due today.



> Great! You're up to date.



Les écrans vides doivent expliquer ce qu'il se passe.


---

345. ÉTATS D'ERREUR

Exemple :

> Something went wrong.



Puis :

> Please try again.



Lorsque possible, proposer une action :

Retry


---

346. CONFIRMATIONS

Pour les actions potentiellement destructrices :

confirmation ;

explication ;

possibilité d'annuler.



---

347. ANIMATIONS

Les animations devront être discrètes.

Elles pourront servir à :

signaler une transition ;

montrer une progression ;

confirmer une action.


Elles ne devront jamais ralentir l'apprentissage.


---

348. GAMIFICATION

La gamification restera secondaire.

Le système pourra utiliser :

badges ;

progression ;

séries ;

objectifs.


Mais il ne devra pas devenir un jeu qui détourne l'attention de la maîtrise linguistique.


---

349. DESIGN DU SCORE

Le score devra être affiché clairement.

Exemple :

87 %

Puis :

Passed

Le pourcentage doit rester l'information principale.


---

350. DESIGN DE LA PROGRESSION

Le système devra toujours distinguer :

Completed

et

Mastery

Exemple :

> Course completion — 78 %



> Skill mastery — 71 %




---

351. PAGE DE PROCLAMATION

Cette page devra être visuellement plus prestigieuse que les pages ordinaires.

Elle pourra présenter :

CONGRATULATIONS!

You have successfully completed the program.

Puis :

87 %

100 % completed

et les domaines maîtrisés.


---

352. ATTESTATION

Une interface permettra :

View Certificate

et éventuellement :

Print / Export

La version PDF pourra être produite dans une étape technique ultérieure.


---

353. DESIGN DU CERTIFICAT

Le certificat devra être :

sobre ;

professionnel ;

imprimable ;

lisible ;

clairement identifiable comme document du centre.



---

354. MODE SOMBRE

Le dark mode pourra être prévu dans l'architecture.

Cependant, il ne sera pas prioritaire pour le MVP.

Priorité :

Light theme excellent

avant :

Light + Dark incomplets.


---

355. INTERNATIONALISATION

Même si le centre commence en français/anglais, l'architecture devra permettre ultérieurement d'ajouter d'autres langues.

Le contenu linguistique lui-même devra cependant conserver sa logique pédagogique.


---

356. MICROCOPY

Les textes de l'interface devront être courts et cohérents.

Exemple :

Préférer :

Start lesson

à :

Click here to begin the lesson.

Préférer :

Review now

à :

You can click on this button to review the items that require revision.


---

357. TON DE L'INTERFACE

Le centre devra adopter un ton :

encourageant ;

professionnel ;

direct ;

respectueux ;

non infantilisant.


Exemple :

Keep going. You're improving.

plutôt que des messages excessivement enfantins.


---

358. COHÉRENCE TERMINOLOGIQUE

Un même concept devra toujours porter le même nom.

Exemple :

Si l'application utilise :

Review

elle ne devra pas alterner sans raison entre :

Review ;

Revision ;

Relearn ;

Practice again.


Le vocabulaire de l'interface devra être défini dans un glossaire interne.

360. EXPÉRIENCE DU PREMIER JOUR

Le premier accès devra être particulièrement soigné.

Parcours :

Welcome

↓

How the program works

↓

Diagnostic

↓

Results

↓

Recommended starting point

↓

Day 1

L'utilisateur doit comprendre rapidement le fonctionnement du centre.


---

361. DIAGNOSTIC INITIAL

Le diagnostic initial devra être visuellement présenté comme une étape importante mais non intimidante.

Message possible :

> Let's find your starting point.



Il ne s'agit pas d'un examen sanctionnant.

Il sert à déterminer les besoins.


---

362. RÉSULTAT DU DIAGNOSTIC

Exemple :

> Your starting profile



Grammar — 68 %

Conversation — 54 %

IT English — 21 %

Listening — 86 %

Le système expliquera ensuite :

> Your program will focus more heavily on these areas.




---

363. PERSONNALISATION

La formation restera structurée sur 20 jours, mais certaines activités pourront être adaptées selon les résultats.

Par exemple :

un étudiant faible en conjugaison recevra davantage d'exercices de conjugaison.

Un étudiant déjà fort dans un domaine pourra recevoir moins de répétitions élémentaires et davantage de pratique contextuelle.


---

364. EXPÉRIENCE DE FIN DE JOURNÉE

À la fin d'une journée pédagogique, le système pourra afficher :

Day completed

Today's score

Skills improved

Items to review

Tomorrow

Cela crée une continuité entre les journées.


---

365. DESIGN MOBILE DES EXERCICES

Les réponses devront être faciles à toucher.

Éviter :

petits boutons ;

texte trop dense ;

longues listes horizontales ;

interfaces nécessitant un zoom.



---

366. DESIGN DES QUESTIONS À CHOIX

Les réponses devront être présentées sous forme de grandes zones cliquables.

Exemple :

A. deploy

B. deployed

C. deploying

Chaque option devra être facilement sélectionnable.


---

367. DESIGN DE PRODUCTION

Pour les réponses écrites, le champ devra :

être suffisamment grand ;

afficher clairement la consigne ;

permettre plusieurs lignes ;

indiquer le nombre de caractères si nécessaire ;

conserver la réponse avant soumission.



---

368. PRÉVENTION DE PERTE

Pendant une évaluation importante, les réponses devront être sauvegardées lorsque techniquement approprié.

Une fermeture accidentelle du navigateur ne devra pas nécessairement détruire toute la tentative.


---

369. DESIGN DE LA NAVIGATION PÉDAGOGIQUE

L'utilisateur devra toujours avoir une action évidente :

What should I do next?

La réponse devra être visible.


---

370. RÈGLE « ONE PRIMARY ACTION »

Chaque écran pédagogique important devra avoir une action principale.

Exemple :

Leçon :

Continue

Évaluation :

Start assessment

Résultat :

Review weak areas

Cela évite de disperser l'utilisateur.


---

371. DESIGN DES ÉLÉMENTS VERROUILLÉS

Un contenu verrouillé devra indiquer :

qu'il est verrouillé ;

pourquoi ;

ce qu'il faut faire pour le débloquer.


Exemple :

> Locked



> Pass Level 3 Assessment with at least 75 %.




---

372. DESIGN DU SUCCÈS

Une validation devra être visible sans être excessive.

Exemple :

Level 3 Passed

Score: 84 %

Next level unlocked.


---

373. DESIGN DE L'ÉCHEC

L'échec ne devra pas être présenté comme une condamnation.

Exemple :

Not passed yet

Score: 68 %

You need 7 more percentage points.

Puis :

Review recommended


---

374. PRINCIPE PSYCHOLOGIQUE

Le système doit transformer l'échec en information.

L'utilisateur doit comprendre :

> « Voilà précisément ce que je dois améliorer. »



et non :

> « Je suis mauvais en anglais. »




---

375. RESPONSIVE DASHBOARD

Sur desktop, plusieurs cartes pourront être affichées côte à côte.

Sur mobile, elles seront empilées verticalement.

Le contenu devra rester prioritaire sur la décoration.


---

376. DESIGN DES TABLEAUX

Les tableaux devront être évités sur mobile lorsqu'ils ne sont pas nécessaires.

Une information telle que :

IT English — 78 %

sera généralement mieux présentée sous forme de carte ou de ligne de progression.


---

377. DESIGN DES STATISTIQUES

Les statistiques importantes devront être compréhensibles en moins de quelques secondes.

Éviter les graphiques compliqués simplement pour « faire professionnel ».


---

378. ACCESSIBILITÉ LINGUISTIQUE

Les instructions de l'interface pourront être en français au début si nécessaire, tandis que le contenu pédagogique cible l'anglais.

Progressivement, certaines interfaces pourront passer à l'anglais.

Cela devra être configurable.


---

379. OBJECTIF FINAL DE L'UX

L'utilisateur doit pouvoir utiliser la plateforme sans avoir besoin de connaître l'informatique.

Il ne doit pas avoir à comprendre :

base de données ;

API ;

serveur ;

fichiers ;

architecture.


Il voit simplement :

Learn → Practice → Review → Assess → Progress.

380. FIN DE LA TRANCHE 7

La conception UX/UI est maintenant définie au niveau fonctionnel.

Nous avons donc :

1/8 — Compréhension et fondations

2/8 — Feuille de route / architecture directrice

3/8 — Architecture fonctionnelle

4/8 — Architecture technique

5/8 — Programme pédagogique

6/8 — Évaluation et maîtrise

7/8 — UX/UI et expérience utilisateur

Il reste maintenant UNE SEULE TRANCHE : 8/8.

Elle sera la tranche opérationnelle finale.

Elle transformera tout ce qui précède en un véritable plan de chantier :

structure définitive du projet ;

Todo maître ;

Tracker ;

ordre exact des tâches ;

dépendances ;

jalons ;

MVP ;

construction avec VS Code ;

utilisation d'Antigravity 2.0 ;

tests ;

validation de chaque bloc ;

préparation des contenus ;

mise en ligne ;

Vercel ;

services gratuits Google ;

sauvegardes ;

maintenance ;

système de versions ;

procédure de mise à jour ;

checklist de lancement ;

critères permettant de déclarer officiellement le centre terminé et opérationnel.
